Problem

Engineering is more than passing a coding interview. You are not asked to invert a binary tree on a whiteboard; you debug a production race condition, optimize a slow query, or fix a broken CI/CD pipeline. Most practice platforms live in a LeetCode vacuum: a text editor and a prompt, disconnected from actual infrastructure. We wanted the environment to be as much of the challenge as the code.

What it does

real_work is a marketplace of engineering labs that run in fully isolated Docker containers. You get a full Linux environment, not just an editor, shown as a virtual desktop in the browser. Nothing to install; containers deploy in the cloud.

  • Labs cover backend performance, distributed-systems debugging, DevOps, web, game dev, and penetration testing.
  • Progress persists: when you leave, the container state is committed to an image and stored on a cloud registry so you resume exactly where you stopped.
  • Authors can plug a custom grader into an API.
  • Anyone can publish a challenge from a GitHub repo or a portable Docker image. Users rate, comment, and discuss strategies.

How we built it

We built real_work at the Catapult 2026 Hackathon. Next.js 15 (App Router) and Tailwind CSS on the front end. Supabase (PostgreSQL) for auth, real-time data, and storage for thumbnails and avatars. A custom Node.js / Docker orchestration layer manages container lifecycles, port mapping, and state persistence. The challenge creator is a multi-step wizard that parses a GitHub repo, extracts function signatures, and bakes author config into a reusable image.

Hard parts

Volume mounts were not enough for resume. We moved to a docker-commit workflow so progress survives sessions without bloating the database. Docker on Windows (PowerShell / WSL) vs Linux needed path sanitization and permission handling. Running arbitrary user code meant multi-layer isolation so containers stay sandboxed.

Result

A VM-like resume: close the browser, come back to the same terminal. A creator wizard that turns a raw GitHub URL into a solvable lab in under a minute. The whole solve path stays on the site. We learned the Docker Engine API (layering, commits, dynamic ports) and used Next.js Server Actions to launch containers without putting that work on the client.

Next
